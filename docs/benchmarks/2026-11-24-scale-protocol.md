# Scale benchmark protocol (fixed before any data was fetched)

Written and committed on 2026-11-24 before downloading a skill, generating a
query, or running an arm. Everything below is a rule, not a result. Deviations
found necessary later are listed in the results document, not edited in here.

## Question

How do the default gate and the opt-in judges behave as the corpus grows, on
skills and queries that nobody on this project wrote or tuned against?

## Corpus

- Candidates: the skills listed on `https://skills.sh/trending` and then
  `https://skills.sh/` on 2026-11-24, in page order, saved as
  `bench/scale/candidates-2026-11-24.json` (745 entries, 99 sources).
- A candidate is accepted, in list order, unless one of these holds:
  1. its source is not a GitHub `owner/repo`;
  2. a skill with the same skill id (case-insensitive) was already accepted;
  3. its source already has 20 accepted skills;
  4. no `SKILL.md` whose parent directory is named exactly like the skill id
     (then case-insensitively) is found in the repository's default-branch
     tree, or the file cannot be fetched;
  5. the repository's own parser (`skill_rag.parser`) rejects the file;
  6. the description is shorter than 40 characters or the body shorter than
     200 characters;
  7. a skill with the same frontmatter name (case-insensitive) was already
     accepted.
- Only `SKILL.md` is downloaded, into `var/bench/scale/pool/` (not committed,
  not installed into any harness, never executed). The manifest of accepted
  skills with their Git blob SHAs is committed.

## Split

The accepted names are shuffled once with `random.Random(20261124)`.

- Targets: the first 50. They are in every corpus.
- Held-out: the next 50. They are in no corpus.
- Distractors: the rest, in shuffled order.
- Corpus sizes: 50, 100, 200, 400 = the targets plus the first 0, 50, 150, 350
  distractors. If fewer than 450 skills are accepted, the largest size becomes
  the largest multiple of 50 the pool supports.

## Queries

Generated by `gpt-6.2-sol` through the Responses API, one request per skill.
The model sees only the skill body with the frontmatter removed, cut to 6,000
characters, so it never sees the description that retrieval and the judges
use. The developer message, verbatim:

> Below is the body of an "agent skill": instructions an AI coding agent loads
> when a user's request calls for them. Write requests that a real user might
> type to an AI agent for which loading this skill would clearly be the right
> move. Each request is one or two sentences and describes the user's own
> concrete task or problem. Do not mention the skill, its name, or that a
> skill exists. Do not copy distinctive phrases from the text. Korean requests
> must read as natural Korean; technical terms may stay in English. Return
> exactly the number of requests asked for in each language.

- Targets: 2 English and 2 Korean requests each, expected = that skill
  (200 positives).
- Held-out: 1 English and 1 Korean request each, expected = no skill
  (100 negatives).
- A generated request that contains the skill's name (case-insensitive, with
  hyphens or spaces) is regenerated once and dropped if it still does. No
  other request is edited, filtered, or replaced by hand.
- The same 300 queries are used at every corpus size.

## Arms and settings

All at shipped defaults, through `mcp_server.search_skills`
(`bench/jev_rerank_ab.py`), `k = 5`:

- `gate`: rerank off.
- `jev`: `SKILL_RAG_RERANK=jev`, SDK default model, 16 candidates, threshold 0.5.
- `openai`: `SKILL_RAG_RERANK=openai`, `gpt-6-luna`, 16 candidates, threshold 0.5.

No threshold, prompt, candidate count, or hint table is changed after results
are seen. The threshold sweep the runner prints is reported as sensitivity
only.

## Metrics

Strict (primary):

- recall@1 and recall@5 on positives against the single expected skill.
- no-match accuracy on negatives: the arm returned nothing.
- mean response size in characters.

Adjudicated (secondary), because a large community corpus contains several
skills for the same job and a held-out skill may have a twin in the corpus.
`gpt-6.2-sol` is shown the query and the arm's first hit (name, description,
first 2,000 characters of the body) and answers whether loading that skill
would genuinely help with this specific request, same task on the same
product, platform, or technology. Verbatim developer message:

> You are checking a skill recommendation. You get a user's request and one
> agent skill (name, description, and the opening of its instructions).
> Decide whether loading this skill would genuinely help with this specific
> request: it must cover the same task on the same product, platform, or
> technology. Sharing a topic or vocabulary is not enough. Answer as JSON.

- adjudicated recall@1: the first hit is the expected skill or is judged to fit.
- adjudicated no-match: the arm returned nothing, or its first hit is judged
  to fit (an acceptable answer rather than a false alarm).
- Each (query, skill) pair is adjudicated once and reused across arms and sizes.

Uncertainty: 95% percentile bootstrap over queries, 2,000 resamples, seed
20261124, for each arm and size.

## Known limits, accepted in advance

- The query generator and the `openai` judge come from the same vendor.
- Generated requests are not real usage.
- Trending lists favor recently promoted skills and include near-copies
  published under different owners; rule 2 removes same-id copies only.
- Single run per configuration; network latency varies.
